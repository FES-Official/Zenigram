# Zenigram App

Zenigram is a Next.js social app with credentials/Google auth, posts, comments, likes, profile privacy, messaging, clips, stories, and the Stories Globe.

## Run locally

```bash
npm install
npm run dev
```

Open `http://localhost:7860`.

For a production-like local run:

```bash
npm run build
npm start
```

## Environment

Create `.env.local` locally and configure the same variables in your hosting environment:

```env
NEXTAUTH_SECRET=
NEXTAUTH_URL=http://localhost:7860
NEXT_PUBLIC_APP_URL=http://localhost:7860
NEXTAUTH_URL_INTERNAL=http://localhost:7860
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
AWS_REGION=
AWS_DYNAMODB_REGION=
AWS_S3_REGION=
AWS_BUCKET_NAME=
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
DYNAMODB_TABLE_NAME=linkex-app
NEXT_PUBLIC_MAPBOX_TOKEN=
PORT=7860
```

`AWS_DYNAMODB_REGION` controls DynamoDB and `AWS_S3_REGION` controls S3. When the two services use the same region, `AWS_REGION` may be shared. The app no longer requires static AWS access keys when the AWS runtime provides credentials through its normal credential provider chain, so prefer an IAM role on EC2 or another workload identity over long-lived keys.

Google sign-in is enabled when both Google variables are present. Credentials sign-in remains available without Google OAuth configuration.

## AWS storage

The browser asks `/api/media/upload` for short-lived signed requests and uploads files directly to private S3. The server verifies ownership and object metadata before a post, clip, or story stores the object reference.

Images and smaller uploads use signed `PutObject`. Large videos can use S3 multipart upload with independent part retries. Incomplete multipart uploads should be removed by an S3 lifecycle rule.

Application metadata uses DynamoDB, including users, posts, clips, stories, comments, likes, support relationships, notifications, reports, invitations, saved content, collections, conversations, and messages.

S3 objects remain private. Read URLs are short-lived signed URLs generated by the server.

Run the storage setup script after configuring AWS credentials or an AWS IAM role:

```bash
npm run aws:setup
```

## Deployment

### Vercel

Vercel is suitable for the Next.js request/response side of Zenigram, including the API routes, but the repository also contains a custom Node HTTP server that hosts Socket.IO. That long-lived realtime server should not be assumed to run as a persistent WebSocket process on a serverless deployment. For production realtime messaging, either run Zenigram's custom Node server on a persistent Node host or move realtime transport to a dedicated realtime provider and keep the Next.js app on Vercel.

Set `NEXTAUTH_URL` and `NEXT_PUBLIC_APP_URL` to the final HTTPS origin in production. Never commit `.env.local`, AWS secrets, `NEXTAUTH_SECRET`, Google client secrets, or private Mapbox tokens.

### Self-hosted Node

The repository's `server.js` starts both Next.js and Socket.IO on the configured port:

```bash
npm run build
npm start
```

Put the Node process behind HTTPS/reverse proxy infrastructure and set `NEXT_PUBLIC_APP_URL`/`NEXTAUTH_URL` to the public origin.

## Security and maintenance

The application validates authenticated ownership for uploaded S3 objects, keeps S3 objects private, uses short-lived signed read URLs, protects account mutations with session checks, and applies baseline browser security headers.

Before releasing a production change, run:

```bash
npm ci
npm run lint
npm run build
```

The GitHub Actions workflow performs the same dependency installation, lint, and build validation for pushes and pull requests targeting `main`.
